## 任务：纯照片模式无法识别 JPG —— 全管线排查、修复、覆盖交付版本

### 根因（架构级，非扩展名问题）
`discover_items` 只扫描 `00_raw` 下的点云/网格文件（`formats=["ply"]`）。
场景②"纯照片三维重建"下 `00_raw/<item>` 是空目录，`_scan_files` 返回空
→ 不 append 任务 → `tasks=[]`，`00_photo/<item>/*.jpg` 从未被读取。
表象是"JPG 不被识别"，实际是**任务发现阶段就断了**。

附带发现 4 个真实缺陷：
1. 图像扩展名白名单在 7 处模块各写一份，口径不一致：
   `sfm_solve._prepare_photos` 缺 `.tif`（导入通过、S1 静默丢弃）；
   `.jfif` / `.jpe`（Windows/浏览器常见 JPEG 扩展名）全线不认。
2. 向导照片区拖入多张 JPG 时，`paths()[0]` 被当作"照片文件夹"，
   校验报「照片位置不是文件夹：xxx.jpg」——用户感知即"JPG 不被识别"。
3. `_auto_root_from_photo` 对普通照片目录取 `dirname`，会在盘符根
   （如 `D:\`）创建 `00_raw/00_photo`。
4. CLI `batch --dry-run` 与 `BatchProcessor.run` 各自调用 `discover_items`，
   新增参数只改一处会导致"预览 0 尊、实跑有任务"。

### 修复
- 新增 `src/h3d/core/media.py`：`IMAGE_EXTS`（jpg/jpeg/jpe/jfif/png/tif/tiff）、
  `is_image_file` / `list_images` / `count_images`；全项目 7 处白名单统一收敛。
- `discover_items(raw_dir, formats, photo_dir=None, allow_photo_only=False)`：
  候选条目名 = raw 子目录 ∪ photo 子目录；无几何但有照片 → 纯照片任务
  （`Task.photo_paths` 记录图像，`raw_paths` 为空）。
- 新增 `Task.photo_paths` 字段。
- 新增 `discover_from_config(cfg)`：任务发现唯一入口，与 `sfm_solve.enabled` 联动；
  `BatchProcessor.run`、CLI `validate`、`batch --dry-run` 全部改走它。
- `sfm_solve._photo_dir_for`：`00_photo/<item>` 不存在但根下有图片时返回根目录（平铺兜底）；
  S1 入口改用 `list_images` 判空，`n_photos` 同口径。
- GUI：`DropArea(collapse_to_dir=True)` 多图拖入自动收敛公共父目录；
  普通照片目录以自身为项目根。
- `h3d_gui.spec` hiddenimports 增加 `h3d.core.media`。

### 验证

## 任务二：文件选择板块无法选中 JPG/PNG（r3）

### 根因（GUI 层，与 r2 的任务发现无关）
`DropArea._browse` 只用 `accept_dirs` 单一开关分流。照片区
`accept_dirs` 默认 `True` → 双击进入 `QFileDialog.getExistingDirectory`，
**该对话框只列目录、不列文件**，任何 JPG/PNG 都不会显示。且文件对话框
未设任何名称过滤器。r2 修的是"拖入/任务发现"，本次是"点选"路径，两条独立链路。

### 修复
- `media.image_dialog_filter()`：由 `IMAGE_EXTS` 生成过滤器，与校验同源。
- `DropArea(browse_mode=...)`：浏览模式与 `accept_dirs` 解耦；
  照片区固定 `files`（`getOpenFileNames` 多选）；`browse_dir()` 保留整目录导入。
- `_collapse()` 单文件边界：只选 1 张时 `commonpath` 返回文件本身，
  需再上提一级，否则报"照片位置不是文件夹"。
- `_add_many()` 成为拖拽/对话框唯一落盘入口；照片区单值语义（改选即替换）。
- `infer_root_from_photo()` 抽出：普通照片目录取**上级**（不污染素材目录），
  父级为盘符根时退回自身。修正 r2 中"取自身"导致的测试冲突。
- 向导照片行加「选择照片…」「选择文件夹…」两个显式按钮，右键同步提供。
- 新增 `tests/test_gui_picker.py` 16 项（fake QFileDialog 注入，无需真实弹窗）。
- CHANGELOG 记 v1.1.0-r3。

## 任务三：兵马俑实机 S1 失败（r4）

### 现象
`E:\兵马俑照片` 30 张尼康单反照（4496×3000 → 预处理 2399×1601），
场景②纯照片。report 显示 S1 失败、状态表全空、无任何可视化产物。

### 根因（状态管理，非照片问题）
`run_colmap_sparse` 每次直接复用 `<workspace>/database.db`，**从不清理**。
用户重试时在**上一次的半写入库**上追加 → 唯一约束冲突 →
`SQLite error: constraint failed` → COLMAP abort（exit 3221226505 / 0xC0000409）。

证据链：
- `failures.csv` 显示崩溃在第 4 张，且 `Camera: #2`（代码写死 single_camera 1，
  正常应恒为 #1）→ 库里已有相机记录。
- 残留库 `cameras=3 / images=30`，images 1-4 绑 cam1、5+ 绑 cam3，cam2 成孤儿。
- **空库对照实验**：同 30 张、同参数 → 30/30、全部 Camera #1、EXIT=0（1.6 分钟）。
- 残留库若已完整（30 张齐），COLMAP 会跳过已有图像不崩 → 解释了"重试就好了"。

### 修复
- 新增 `_reset_sparse_state()`：删 database.db/-wal/-shm/-journal + 清空 sparse/，
  **保留 photos_small**（预处理成果）。只在全量路径调用，增量注册不受影响。
- 新增 `_dump_step_log()`：每步写 `logs/colmap_stepN.log`（命令+exit+完整 stdout/stderr）。
- 新增 `_error_tail()` + 按特征给诊断（constraint failed / 0xC0000409 / CUDA / 路径）。
- `RunManifest.record_fail(elapsed_s=)`；`_isolate()` 记真实耗时（原恒 0）。
- 报表：状态表纳入 S1/P1 + "产物/异常摘要"列 + 顶部统计横幅 + 失败明细 pre-wrap
  + 诊断建议块 + 章节编号修正（原两个"五、"）；failures.csv 加"耗时(s)"。
- GUI：预览回退 80_export→30_dense→10_dense→fused.ply；无模型时 show_text 显示原因；
  失败时打印 report 与 logs 路径；open3d 按钮按实际文件启用；matplotlib 配中文字体。

### 验证
- 干净库 S1 实测：7 分 41 秒，**30/30 注册、cameras=1、13990 点**，三步日志落盘。
- 污染库对照：30/30 注册但 cameras=3（引用 2 个）、13971 点。
- 新增 `test_sfm_reset.py`(11) + `test_report_failure.py`(8)；修正受影响的
  `test_sfm_solve.py::test_success_with_mock_colmap`（模型改由 mapper 步骤现场产出）
  与 `test_csv_export.py`（字段新增耗时列）。
- 交付 PDF：14 页 / 3533 中文字符 / 0 豆腐块。

### 经验
- **"能跑通"≠"正确"**：注册率正常也可能相机模型已被污染（本次 cam1/cam3 分裂仍 30/30）。
- 外部程序的输出目录是**有状态**的；全量重建必须先划清状态边界。

### 根因一（致命回归，r5 引入）
`runner.py` 调用了 `substep_of(line)` 却**没加进 import**。
`BatchRunner.run()` 在转发第一行日志后抛 NameError，**QThread 静默结束**：
Qt 不打印 Python 线程异常 → 日志不再刷新、进度条不动、阶段灯不亮，
表现与卡死完全一致。
修：补导入 + 整个解析循环包 try/except + `[错误] 日志解析线程异常` + 失败汇总。

### 根因二（假 30/30）
`_depth_progress()` 遍历 `99_runs/sfm_tmp` 下**所有**造像取最大值。
上一轮残留 `relic_666` 真有 30 张 → best=(30,30)，永远停在 30/30。
修：新增 `item_of()` 从 `▶ S1 开始：<编号>` 取当前造像，
只统计该目录；分母改用 `photos_small` 照片数（与 COLMAP 的 n/N 同源）。

### 根因三（乱码）
打包版子进程 stdout 是 cp936，GUI 按 utf-8 读。
**`PYTHONIOENCODING` 在 PyInstaller 里不生效**（bootloader 先建流）→
必须 `sys.stdout.reconfigure(encoding="utf-8")`，新增 `launcher._force_utf8_stdio()`。

### 附带发现：patch_match_stereo 跑两遍
`colmap_step12.log` 里 `Processing view n / 30` 出现 **60 次**（1..30 再来一遍）：
第一遍 photometric（*.photometric.bin），第二遍 geom_consistency（*.geometric.bin），

## r6.2 稠密阶段耗时归因（实机 1.5 h 无产出复盘）

### 本次实机时间线（relic_001BMYyyyy）
- 21:40:03 S1 开始 → 21:47:34 稀疏完成（30/30 注册、1 相机、13990 点、0.497 px）
- 21:47:37 → 22:31:12 深度图第一遍 30 张（2615 s，87 s/张）
- 22:33:08 → 22:47:38 几何校验第二遍只完成 6 张 → **3600 s TimeoutExpired**
- 合计 4055 s（67.6 min），另一尊 relic_666 又从头跑，用户 22:56 取消

### 六条根因（按影响排序）
1. **两个批处理进程并发**（PID 26048 旧轮 20:36 / 26332 新轮 21:39）。新轮
   21:40:11 清 `<ws>/dense` → 旧轮 21:45:49 写 DSC_0037.geometric.bin 报
   `Check failed: (file).is_open()` + `Could not create logging file`（cwd 被删）
   → 旧轮 69 min 作废。两进程抢 GPU：单张 45 s → 87 s（第一遍）→ 145 s（第二遍）。
   manifest 被两边交替覆写（22:48:04 落盘的是旧轮记录）。
2. **4 尊造像 = 同一批 30 张照片**。model_analyzer 三份 sparse 完全一致
   （Points 13990 / Obs 55242 / 0.496871 px）→ 计算量 ×4。
3. **geom_consistency=true 跑两遍**，第二遍约 70 min，总需求 6815 s。
4. **稠密沿用 2400 长边**（3.84 MP）；1600 长边只要 1.71 MP（×0.44）。
5. **超时 3600 s 写死且覆盖整条命令** → 需求 6815 s 必然腰斩。
6. **超时后不可续算**：`run_dense_stereo` 入口无条件 `rmtree(stereo)`，
   35 个 bin（30 photometric + 5 geometric）被下一轮删光。

## r6.3 场景①（带扫描件）缺陷排查与修复

用户要求「带着照片场景的问题遍历扫描件场景」。方法是把场景② 的六类问题当探针逐条映射，
结果发现场景② 的问题基本已被 r6.2 通用修复覆盖，但场景① 独有三个结构性缺陷。

### 四组实机实验（内置示例：椭球 8000 点 + 16 张 640px）
| 实验 | 场景 | 结果 |
|---|---|---|
| A | 标准（激光+照片） | S1 56s(16/16) → M1 4363 点 → M3 19829 面 → M4 照片投影(16 相机) → M5 27.15mm pass |
| B | 只有扫描件（删 00_photo） | **修复前 done=0 failed=1**；修复后 done=1，M4 降级顶点色，M5 28.17mm |
| C | 勾选稠密 dense=true | **修复前** 并入 146453 点 → 33758 面 / 36.78mm / 覆盖 2.32%；**修复后** 跳过合并 → 19829 面 / 28.02mm / 5.87% |
| D | 多站（2 站） | M2 fitness=1.000、M3 24863 面、M5 22.00mm pass（场景② 不存在此路径） |

### 七项缺陷
- **D1 致命**：场景① 无照片 → S1 抛 RecoverableError → break → M1~M6 全不执行。
  向导模板 `sfm_solve.enabled=true`，用户只放扫描件必踩。报错路径还是回退路径（指向项目外）。
- **D2 严重**：有激光几何时勾选稠密 → M1 无条件并入 SfM 点云 → 几何全面劣化。
- **D3 严重（同类复发）**：M1 的 novel 计算用 `np.asarray` 但 `runner/__init__.py` **没有
  `import numpy as np`** → NameError 被 `except Exception` 吞掉 → **P3 在线标定从未生效**。
  证据：手动调 `online_novel_threshold` 得 0.4/0.0，M1 内部对远距离 dense 也报 0.0。
  与「P3 增量注册静默失效数周」完全同型，是第二次犯。
- **D4**：X2 照片目录写 `dirname(task.root)/00_photo/<item>`，多一层 → 色卡定位永不生效，
  静默退回随机采样，ΔE 长期失真。
- **D5**：S1 报错只打印解析结果（回退路径），不给正确布局。
- **D6**：可选阶段关闭仍打「▶ X1 开始」，界面亮一盏永不完成的灯。
- **D7**：`coverage_ratio` 实为纹理图集像素利用率（33758 面只占 1024² 的 5.87% 属正常），
  被误读为网格覆盖率。本轮只澄清口径未改计算。

### 修复要点
- `batch_processor`：`OPTIONAL_STAGES` + `_degrades_on_failure(stage, task)`
  = `stage in {S1,P1,X1,X2} and bool(task.raw_paths)`。场景① 可选阶段失败**降级跳过**
  （`_degrade_optional`：WARNING + manifest 写 `degraded=True`/`reason`，不计入 failures），
  场景② 仍整尊失败。主流程与 `_run_task_worker` 两处同构。
- `runner/__init__.py`：补 `import numpy as np`；except 记 `dense_novel_error`；
  M1 新增门控 `if outputs and novel < 0.15: 不合并`（`_DENSE_MERGE_MIN_NOVEL`，
  metrics 增 `dense_merged`）；M4 photo 失败降级顶点色（`paint_mode_effective`/
  `fallback_reason`）；X2 优先 `task.root/00_photo` + 新增 `checker_source`。
- `sfm_solve`：报错给出正确布局 + 平铺备选 + 「只有扫描件请关闭 sfm_solve.enabled」。
- `_stage_enabled` 预判「▶ 开始」日志（P1 还要求 paint_mode≠photo）。
