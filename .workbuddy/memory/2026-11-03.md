# 2026-11-03

## capture_meta 位姿约定错了 —— 19/30 台相机一直在投空（ADR-0013，提交 de43bb4）

### 起点
`projected_cameras = 11/30` 一直没解释。逐台量「能看到多少纹素」：11 台 6%~83%，
**19 台一个都没有**。不是权重问题（看得到却不被选的是 0 台）。

### 根因
`90_meta/relic_001_capture_meta.json` 写于 **2026-09-15「坐标系修复」之前**，存的是
**原生 COLMAP 格式**（`R_co` + `tvec`，前方 **+Z**）。管线按新约定（`t`=相机中心、
前方 −Z）读它，等于把 `tvec` 当成了相机位置。

逐条比对 `images.txt` 确认：`R_json = -R_parse`、`t_json = R_parse @ C_parse`。

**决定性验证**（用 COLMAP 自己的 points3D.txt，必然能投回画幅）：
- 当原生 (R_co,tvec) 读 → **95.6%，30/30 台**
- 按管线 (R,C) 读 → 5.25%
→ 文件是对的，**读法错了**。

### 判据不能用 det(R)
第一版我用 det：新约定 `R = -R_co` 确实翻符号。写完测试才发现它**会误伤合法文件**
——`R` 与 `-R` 给出**完全相同的 u/v**，只翻 z 的符号；手写的合法位姿完全可以
det=+1（`test_atlas_delivery` 里就有一个这样的合成位姿，被这个判据读坏）。

### 实装
`normalise_pose_convention(images, cameras, probe_points)`：用 SfM 稀疏点当探针
（M4 本来就要读它做对齐），两种解释各投一遍，转换后更高且过阈值 → 就地转换；
**判不出来就报 unknown 且不动**（猜错方向比不猜更糟）。调用点在
`texture_mesh_from_photos` 里、**任何投影之前**（含对齐预检）。
`CACHE_VERSION` 2 → 3。

### 这条修复推翻了之前的结论（重要）
| | 修前 | 修后 |
|---|---|---|
| coverage_ratio | 0.5681 | **0.0000** |
| cameras_blind | 19/30 | **30/30** |

之前那个 57% 覆盖率、87.6% 岛内填充、X3 的 0.31%/4 处，**全部建立在读错位姿上**。
那 11 台「能投上」也不是真对齐——`in_frame` 只判「落在画幅矩形内」，不判「落在
文物上」。它同时骗过了 ADR-0011 的「已在画幅内→跳过对齐」闸门（错位姿下算出
86.7%，正当放行）。

**纪律：任何以位姿为输入的预检，都必须先确认位姿本身可信。**

## ICP 对齐：24 个旋转初值 + 尺度夹带（ADR-0014，提交 cbfbc76）

### 根因
位姿修正后暴露：激光网格与 SfM 不同系（`10_dense` 100% 入画、激光件 0%），必须
对齐。`align_points_to_mesh` 报「包围盒 0.43 倍」被闸门拒。而两边 99% 分位对角线
只差 3%（6.04 vs 6.20），初始尺度 0.966，尺度却掉到 0.43。

同一份数据、只保留旋转平移：
- **单位阵初值（原实现唯一初值）→ 中位最近邻 112% 对角线**（完全卡死）
- 最优旋转初值 → 2.5%（可用）

COLMAP 世界系的轴向由建图过程决定，与扫描仪无关。**尺度漂移是症状，初值是病因。**

### 改
24 个立方体群旋转各跑一遍，取最终中位最近邻最小者；`_SCALE_BAND=(0.6,1.6)` 夹住
尺度（越界就当这步没估出尺度）；`scale_init` 与 `scale_s` 并列进 metrics。
代价约 2 s。

### 自己踩的坑
第一版把初值旋转用在了点上，**却没折进累积 (s,R,T)** → 返回的变换复现不出它自己
算出的点 →「最优候选」按返回变换算回去比单位阵还差。合成凸体上看不出来（都能
收敛），是逐点比对 `work` 才暴露。已加 `test_returned_transform_reproduces_the_working_set`。

### 真机结果
```
对齐    rejected → applied（control_points + nearest_refine），in_frame 0% → 100%
投影    11/30 → 30/30，blind 19/30 → 0/30
覆盖    0 → 0.6332        岛内填充 0 → 0.9998
color_std 32.67 → 16.06   X3: 0.69%/14 处 → 0.73%/18 处，σ 15.65 → 11.30
```

### 需要修正的旧结论
「岛间色调跳变 = 照片白平衡不一致 = 缺色卡」这个归因**要改**。color_std 从 32.67
掉到 16.06 说明很大一部分是「那些相机根本不在看这个位置」。ADR-0012 的实测
（相机增益差异中位 0.0%）仍成立，但归因要改成：**先保证位姿对，再谈光度。**

### 待办
- `normal_visible_fraction` 0.73（<90% 阈值）—— 网格局部法线不一致，下一处可查
- 真机 capture_meta 仍是老格式，建议重跑 S1（现在会 WARNING + 自动纠正）
- 旧 `output/_build/` 下的备份产物对应的是错位姿那版，别拿来比对数字

## normal_visible 0.73 查清：不是法线，是控制点对齐把物体压小了一半（提交 a54ee59）

### 回路
逐面比较相邻面法线（无向边配对）：相邻面反向 **0.08%**，"与多数邻居反向"的面
**0.04%** → **法线是全局一致的**，告警说的"局部翻向"不成立。

### 那 0.73 从哪来
M4 走的是 `control_points + nearest_refine`（没有 00_ctrl 文件，走自动控制点），
不是我探针里的自动 ICP。两条路都"合格"，尺度差 2.5 倍：

| 对齐 | 成品网格对角 | 稀疏点→网格 中位 |
|---|---|---|
| 原始 30_dense | 6.24 | 4.83（77% 对角）|
| **M4 控制点+refine** | **3.27** | 0.443（6.6%）|
| 自动 ICP | 8.02 | 0.151（2.3%）|

稀疏点稳健对角 6.70 → 正确尺度应接近 1.07。**M4 那条把物体压到 3.27。**

决定性验证（把成品网格投回 DSC_0014）：红圈只盖住**头部**、整体向右溢出、
明显偏小；绿圈（自动 ICP）覆盖整个身躯但**仍有残余右移**。两条都不完美，
但控制点那条错得离谱且被判 accepted。

### 改了什么（只改了误诊，没改对齐）
`geo_align.normal_consistency(mesh)` → 相邻面法线反向比例，进 metrics 为
`normal_flip_fraction`；可见性 <90% 时才算。文案分三支：
- flip 高 → 法线真坏了
- flip 低 → **"法线是好的，问题在对齐"**（真机实测 0.00% 走这支）

旧的文案直接断言"法线局部不一致"，我按它查了一整轮才发现病根在对齐——误诊的
代价比没有告警还大。

### 未修（下一步）
1. **控制点+refine 对齐产出错误尺度却被 accepted** —— 质量闸门只看包围盒比值，
   没约束「施加的尺度必须与初值（鲁棒对角比）同量级」。真机 3.27 vs 期望 6.7。
2. **该路径跨运行不确定**：同一输入三次 M4，coverage 0.6335 / 0.6538 / 0.6305，
   normal_visible 0.7401 / 0.7278 / 0.7084。自动 ICP 那条是确定的。
3. 自动 ICP 那条也有残余平移（绿圈右偏），需要另一个判据收口。

## 精化阶段：尺度夹带 + 定种子 + 自报尺度（提交 67c35af）

`refine_mesh_to_points` 里叠着三个缺陷：
1. **尺度完全自由** —— 5 次迭代每次解相似变换，一路把物体压到 0.52
2. **没定种子** —— `sample_points_uniformly` 用 Open3D 自己的随机源，同输入逐顶点
   差 2.9e-3（这就是 coverage 0.6335/0.6538/0.6305 的来源）
3. **不报实际施加的尺度** —— `metrics["scale_s"]` 是第一阶段的，精化改了多少看不出来

改：`_REFINE_SCALE_BAND=(0.75,1.35)` 夹累积尺度；每轮 `_seed_random`；新增
`scale_applied` / `scale_band`，`align_two_stage` 再合成 `scale_total`。

真机：`scale_total` 0.68 → **1.0088**（期望 1.07）。**塌陷消失、运行确定。**

### 但还剩一个 90° 的朝向错
`normal_visible` 仍 0.69。与自动 ICP 比，两条路径的形状主轴差 **90°**
（主轴0 |cos|=0.001）。照片上文物竖直、绿圈（ICP）覆盖正常 → **控制点那条的
旋转是错的**，误差在 `align_mesh_with_controls`（第一阶段）。

**现有闸门抓不到它**：`in_frame` 对齐前是 0（激光系里根本没相机），对齐后任何
把物体搬到相机前方的解都报 1.0，区分不了 0° 和 90°。能区分的量是
**对齐后的 normal_visible**（ICP 0.98 / 控制点 0.69）。

→ 下一片：**两条路径都跑，按对齐后的 normal_visible（或平均 cos）取优**，
    而不是"控制点优先、失败才回退"。

## 对齐择优：两条路径都跑，按「能被正面看到的面比例」取优（提交 6142a93）

### 判据
`visible_score(verts, tris, images, cameras)` = 有多少比例的面能被任一相机正面
看到（cos>0.3），口径 `max(正向, 反向)`（法线整体朝内只是符号约定，不该被罚）。
`choose_alignment(candidates)` 取最高分，并把**每个候选的分数**写进
`align_candidates`（落选的也留，否则下次争论没有依据）。

真机区分度：自动 ICP 0.98 / 控制点 0.69 —— 而 `in_frame` 两条都是 1.0（它区分
不了 0° 和 90°）。

### 同时放宽了质量闸门的尺度带宽 0.30 → 0.45
真机 0.66 被 0.70 卡住判无效，但那只是「稀疏点只覆盖可见面」造成的覆盖范围差异。
闸门职责是拦灾难（2.03 / 0.43 仍被拒，已加测试锁住），细粒度取舍交给 visible_score。

### 端到端**还不稳定**（重要，别当成已解决）
同一份输入三次 M4，`normal_visible` 分别是 0.96 / 0.69 / 0.58。

单测 `align_points_to_mesh` 是确定的（s=0.76409、accepted、diag_ratio 0.8025，
三次完全一致），**但在 M4 里同一份输入报 s=0.77141 并被拒**——说明 M4 喂给它的
几何与 `30_dense` 不是同一份（上游分支改过 mesh），或者 `skip_align` /
`_need_align` 预检在不同次运行下结论不同。

### 下一片（明确）
**候选生成改成无条件**：两条对齐都算、都进 `choose_alignment`，闸门结论只作为
metrics 记录，不再一票否决。这样每次运行都走同一条决策路径，结果可复现。
现在的结构是「控制点优先、失败才回退」，分支是否可用本身就不确定（自动生成控制点
有时凑不齐 3 个），导致落在哪条路上都在变。

## 候选无条件生成：同输入三次跑出同一结果（提交 96fc5f1）

### 上一片为什么"看不出效果"——一个自我强化回路
择优只接在「控制点通过」的分支里，而**分支取决于磁盘上有没有文件**：
`align_points_to_mesh` 成功后会导出 `00_ctrl/<件>/control_points.json`，
下次运行就走控制点那条（实测 90° 旋转错）。真机该文件 mtime 是今天 10:30，
里面只有 3 个点。于是同一输入三次：0.96 / 0.69 / 0.58。

### 重构
- 候选**无条件**生成：identity（基准）+ control_points（有文件就跑）+ auto_icp
  （稀疏点够就跑），**全部从同一份原始几何 verts0 出发**（这就是之前 M4 里
  报 s=0.77141、单独调用报 0.76409 的原因——上游改过 mesh）
- 统一 `choose_alignment` 按 `visible_score` 取优；质量闸门结论只作指标
- identity 胜出时显式 rejected + 理由，不静默
- 控制点导出**只在选中 auto_icp 时**做（否则错误答案自我强化）

### 真机（1024，保留坏控制点文件，连跑三次）
```
择优=auto_icp  候选 auto_icp 0.9805 / control_points 0.968 / identity 0.9037
可见 0.9609  覆盖 0.5872  填充 0.9216   ← 三次一字不差
```
第一次跑后控制点 3→8 点（选中 ICP 才导出），控制点分数 0.626→0.968，仍打不过
ICP（0.9805），所以选择稳定。

### 2048 最终 / 对 X3 的影响
```
coverage 0.5865  island_fill 0.9207  normal_visible 0.9617  in_frame 0.8691
color_std 14.42  projected 30/30  blind 0
X3: 0.3294% / 7 处 / σ 14.78   （上一版 0.6874% / 14 处 / σ 11.30）
```
异常面积与处数**减半**。岛内填充从 0.9998 掉到 0.9207 是**变好了**：那 0.9998
是靠"背面补色"堆出来的，现在要求真有相机能看到（visible 0.96）。

### 纪律（今天第三次同一模式）
**单一候选 + 事后闸门 < 多候选 + 显式判据。** 闸门只能拦"离谱"，拦不住"看着
合理但错"——0.43 倍尺度、90° 旋转都属于后者。而且**候选的可用性本身不能是
随机的**（取决于磁盘上有没有某个文件），否则判据再好也没有可比对象。

形变**，不存在"用形变换岛数"的取舍。

### 法线完全不起作用
原始 / 拉普拉斯平滑 5、20 次 / **强制全 +Z** → 岛数**都是 1890**。
「xatlas 沿法线不连续切图」这个假设被我自己的实验否证。

### 对照实验定位根因
| 几何 | 面数 | 岛数 |
|---|---|---|
| 标准球 | 14160 | **7** |
| 真机 30_dense | 73222 | **1890** |
| 真机简化到 2 万面 | 20000 | **103** |

- 不用简化/平滑换岛数：该网格同时是 M5 精度与 P1 纹理的载体，动几何 = 动测量

- 不动 xatlas 参数：±15% 无观测改善，却引入未验证的默认值变化（hole_fill_px 同类）。
- X3 的「N 处」继续只读作**待复核处数**。

### 下一阶段真杠杆
**M3 泊松参数**（depth / point_weight / density_quantile）——在保持点云覆盖率前提
下减少过度三角化，能同时改善岛数与三角形质量。单独一轮，改完必须重核 M5 rmse。
复查脚本已入库：`scripts/probe_uv_charts.py`

## X3 图斑成因：不在岛边界，是岛内成片暗块（ADR-0016，提交 89197d9）

### 我之前的说法是错的
多轮反复说「X3 图斑是 UV 岛边界伪影」，并据此做了 ADR-0015 的整套尝试。
**从没量过。** 这次量了：

| | 基线 | 7 处图斑 | 富集 |
|---|---|---|---|
| 距未着色 ≤3px | 27.40% | 22.2% | **0.8×** |
| 所在岛 <1000 纹素 | 11.03% | 0.4% | **0.0×** |
| 到未着色区中位距离 | — | 4.1~10.8 px | — |

图斑**比平均位置更靠岛内部**；2185 个岛里 1051 个是碎岛，图斑一个都没进去。

**教训：只看图斑自身的占比没有意义，必须和全图集基线比富集倍数。**

### 图斑是什么
- 与紧邻环带的亮度差：7 处**全部更暗**（−4 到 −90）→ 系统性偏置，不是随机噪声
- 斑内 σ 10~36，与随机岛内窗口 7~29 同量级 → 仍有正常纹理起伏，不是平板
- 排除掩膜/颜色不符：全图集亮度<20 的着色纹素 0.00%，图斑 5351 纹素里 0 个

### 最可能成因
**同一个 UV 岛内部由不同相机拼出的色调台阶**：一个岛由 top-k 相机共同着色，
"哪台胜出"在岛内形成 Voronoi 分界，两侧来自不同曝光/角度。
这也解释了为什么减少岛数无效——**台阶跟着相机分界走，不跟岛边界走**。

### 下一步（决定性）
把**逐纹素胜出相机 id** 落成诊断 PNG（`_L1.0_camera_id.png`）。图斑边界若与
相机分界重合 → 相机拼接台阶；不重合 → 真实表面特征，该当待复核而非噪声。
这个诊断把「猜成因」变成「看图对边界」。

### 口径

伪影"直接扣掉是不对的**——它们不在边界。

## 逐纹素相机 id 诊断：图斑成因判出来了（ADR-0016 追加，提交 2def42f）

### 做了什么
M4 采样时记录**胜出相机下标**，落 16 位 PNG 到 `99_runs/camera_id/<件>_camera_id.png`
（0=未着色，k+1=第 k 台）。**落 99_runs 不落交付目录**——第一版写进 50_tex，被
`test_atlas_delivery` 的「输出目录只有 diffuse.png」断言当场抓住。那个断言的价值
就在这。CACHE_VERSION 4 → 5。

### 判决（与基线比富集，基线 = 着色纹素落在相机分界上的比例 6.94%）
| | 基线 | 图斑均值 | 富集 |
|---|---|---|---|
| 落在相机分界 | 6.94% | **17.0%** | **2.4×** |

逐处含相机数 [5,9,4,2,6,3,**1**]，分界占比 11.2/29.5/23.4/12.4/26.2/16.3/**0.0**%

### 结论分两半
1. **相机分界有贡献但不是主因**：三处 3~4×，但 83% 图斑纹素不在任何分界上。
   注意「占比只有 17% 却显著」不矛盾——一条色调台阶让**一侧整片区域**偏色，
   被检出的是线一侧的面，不是线本身。
2. **第 7 处只由 1 台相机着色**（富集 0.0×）→ 与拼接无关，只能归到「真实表面特征
   或单相机内的光照梯度」。

### 四条假设的最终状态（这条最值钱）
| 假设 | 结论 |
|---|---|
| UV 岛边界 | **排除**（0.8× 反富集，0 处落在碎岛） |
| 掩膜/颜色不符 | **排除**（近黑纹素 0.00%） |
| 相机拼接台阶 | **部分成立**（2.4×，第 7 处除外） |
| 真实表面/单相机光照梯度 | **未排除**，第 7 处只能归这里 |

### 关于「X3 能不能当病害检测用」
现在有实证：至少 1/7 的检出不可能归因于任何管线伪影。**剩下的要看下一件数据**
——一件病害形态明确的文物。在此之前，「N 处」仍只读作待复核处数。

丢东西：**清单说交付 3 件、磁盘只有 2 件，脚本照样 PASS**。

## accuracy.csv 数值核对（ADR-0017 D7，提交 37b8384，已推送）

核验原来只查结构（列数、有数据行）。可这张表是**论文直接引用**的那张：手改一个
数、或某次重算后 CSV 没重新生成，结构检查全都看不见。

### 只核对「manifest 里有唯一来源」的 6 列
`中误差(mm)`←M5.rmse_mm / `覆盖率`←M5.coverage / `相对中误差`←M5.rmse_rel /
`纹理覆盖率`←M4.coverage_ratio / `异常面积`←M5.anomaly_ratio / `图斑数`←M5.anomaly_regions

`中误差口径`/`判定`/`纹理达标` 是**文字与派生结论**，不是可独立复算的数——
把它们也纳入核对等于把同一段判断抄两遍（r16 手写副本）。

### 三条细节，每条都对应一种会误伤的写法
1. **容差跟着单元格自己的显示精度**（半个最小刻度）。报表写的是四舍五入值，
   拿全精度比一定对不上：`62.11` vs `"62.1%"` 会把每条都报成假 FAIL。
2. **`N/A`/`未筛查`/`未标定` 不是「对不上」**，是合法状态。把「没数」当「数错了」
   会逼人去凑数——那是伪造数据的起点。
3. **列名漂移要主动查**：`accuracy_column_drift()` 对照 `ACCURACY_HEADERS`，
   对不上就 WARN。列一改，数值核对会**静默跳过**（r16 根因同款）。

### 真机 + 破坏性
```
relic_001（照片）  核过 12 个数值   PASS 23 / WARN 0 / FAIL 0
batch3（顶点色）   核过 9 个数值    PASS 23 / WARN 0 / FAIL 0
改覆盖率 62.1%→75.0% → [FAIL] …「覆盖率」写 75.0%，manifest 是 62.1
还原 → PASS 23
```
期望值按**单元格精度**印（62.1 不是 62.11），否则读的人会去找一个不存在的偏差。

测试 1323 项绿（+5）。

### 未决
- `纹理清晰度`/`纹理接缝`/`X1` 两列没有唯一来源，暂不核
- CSV 多数据行时只核「第一列 = 目录名」那行（一件一表下够用）

## GUI 核验按钮 + 撞出一个真缺陷：迁移只搬东西不搬账（ADR-0018，提交 cb7bb02）
