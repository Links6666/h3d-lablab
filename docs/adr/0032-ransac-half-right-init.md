# ADR-0032：7° 失败的根因是 RANSAC 的「半对」初值 —— 它比恒等还差

- 日期：2026-11-07
- 状态：已确认（待修，方案见末节）
- 相关：ADR-0031（单线程）、ADR-0021（被拒回退恒等）、ADR-0025（朝向判据）

## 结论先说

> **7° 档失败不是因为 FPFH 半径，也不是几何位姿歧义，而是 RANSAC 给出了一个
> 「半个对」的初值（fitness 0.33、方向差 145°），把 ICP 带到了错误的局部极小。**

从**恒等变换**出发，同一套 ICP 在 7° 档收敛到 **0.031°**、fitness **1.0000**。

## 排查过程（含一次我自己的严重错误）

### 第一步：半径扫描（第一版，结果作废）

第一版脚本手搓 `RegisterConfig(fpfh=r, ransac=r, icp=r*0.5)`，扫 `diag × 0.02~0.18`，
得到「6 个半径最终误差全部 14.00°」，据此写了一版「位姿歧义」的 ADR。

**那份 ADR 已删除**，因为误差公式写错了：

```python
# 错：把注入矩阵当成了真值
c = np.trace(R_reg @ R_inj.T)

# 对：source 被注入 R_inj，配准要把它转回去，真值是 R_inj（不是它的转置）
c = np.trace(R_reg @ R_inj)
```

**识别特征当时就在眼前，我没看出来**：报出的误差恰好是注入角的 **2 倍**
（7°→14.00°、30°→60.00°），这正是「方向反了」的算术指纹。

教训写进方法学：**当一个指标的输出和输入成正比、且比例是 2 时，先怀疑方向**。

### 第二步：半径扫描（第二版，生产配置 + 正确公式）

关键修正：走 `resolve_task_config`（尺度自适应），只按倍数缩放 `fpfh_radius` 与
`ransac_distance`，`icp_distance` 保持不变（否则一次改两个变量）。

真机 `test111.ply`（33,318 点），注入 7° + 0.2% 噪声：

| 半径（×生产值） | 对应内点率 | RANSAC fitness | RANSAC 误差 | **最终误差** | 最终 fitness |
|---|---|---|---|---|---|
| 0.50 | 0.0% | 0.0000 | 7.00° | **0.01°** | 1.0000 |
| 0.75 | 0.0% | 0.0000 | 7.00° | **0.01°** | 1.0000 |
| **1.00（生产）** | 0.2% | **0.3287** | **145.65°** | **29.99°** | 0.2589 |
| 1.50 | 2.3% | 0.7337 | 6.00° | **0.01°** | 1.0000 |
| 2.00 | 2.8% | 0.9766 | 8.25° | **0.01°** | 1.0000 |
| 3.00 | 5.5% | 0.9998 | 8.25° | **0.01°** | 1.0000 |

**6 个里 5 个能解对，唯独生产值（`diag × 0.0162`）失败。**

### 第三步：为什么会这样——「半对」是最糟的状态

看 RANSAC 的行为分三档：

| RANSAC 状态 | ICP 从哪出发 | 结果 |
|---|---|---|
| fitness = 0（彻底失败） | 恒等变换（回退路径） | **对**（0.01°） |
| **fitness = 0.33（半对）** | **RANSAC 解** | **错**（29.99°） |
| fitness ≥ 0.73（基本对） | RANSAC 解 | **对**（0.01°） |

**「彻底没给初值」比「给了个半对的初值」更好。** 因为恒等变换离真值只差 7°，
ICP 有足够的吸引域；而 145° 的错初值把 ICP 带进了另一个极小。

### 第四步：直接验证（决定性的那个实验）

固定点云，只改 ICP 的初值：

| 注入 | 从 RANSAC 初值 | **从恒等变换** |
|---|---|---|
| 7° | 29.98° / fitness 0.2589 | **0.031° / fitness 1.0000** |
| 30° | 0.01°（RANSAC 恰好返回恒等） | 0.045° / fitness 1.0000 |

多初值的候选 fitness（7° 档，从恒等出发）：

```
ransac          fitness=1.0000   ← 收敛后
flip180_axis1   fitness=0.1885
flip180_axis2   fitness=0.1595
```

## 排除掉的原因

| 候选 | 状态 |
|---|---|
| 随机种子（ADR-0024） | 已修 |
| 多线程并行（ADR-0031） | 已修，单线程后 5/5 一致 |
| FPFH 半径「太粗/太细」 | **不是单调关系**：0.5× 与 1.5× 都好，只有 1.0× 差 |
| 对应点内点率 | 0.0% 时反而对（因为 RANSAC 直接失败→回退恒等），不是瓶颈 |
| 几何位姿歧义 | **否定**：恒等出发能解到 0.031°，说明几何上是可分辨的 |
| RANSAC 迭代不足 | 生产值下 fitness 0.33 说明它「找到了一些」，不是没找到 |

## 建议的修复（未实施）

**在多初值候选里加一个恒等变换**：

```python
cands = [("ransac", init)] + flips + [("identity", np.eye(4))]
```

理由：

1. 7° 档从恒等出发收敛到 fitness **1.0000**，而 RANSAC 候选只有 **0.2589**——
   「取 fitness 最高」的既有规则会**自动选中恒等**，不需要改选择逻辑；
2. 代价是多跑一次 ICP（约 +0.3 s），与 ADR-0031 的 0.17 s 同量级；
3. 与 ADR-0021「被拒 → 回退恒等」同一个思路，只是把它提前到候选集里；
4. 风险低：恒等只在**确实更好**时才胜出，不会覆盖已经正确的 RANSAC 解。

**为什么不同时改半径**：1.5× 也能解对，但那是「换了个碰巧不半对的值」，
换件文物可能又落回坏区间。加恒等候选是针对机制本身的修法。
