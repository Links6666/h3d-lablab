# ADR-0030：按局部法向一致性剔除对应点（含法向可靠性闸门）

- 状态：已采纳（默认关闭）
- 日期：2026-11-07
- 相关：ADR-0025（朝向闸门）、ADR-0026（随机消费者）、ADR-0028、
  `docs/文献分析-法向量引导MVS对管线的优化方向.md` P0-2 / P1-1

## 背景

论文（刘建祥等，2026）用「局部法向一致性」``c = (n̂ · n̄ + 1)/2`` 做三件事：
调制特征、加权相似度体、校准代价体。文献分析判断「可低成本落地一条」：
把 c 用在 M2 的对应点筛选上——FPFH+RANSAC 的错配集中在折角、边缘、法向突变处，
而那正是 c 低的地方。

## 决策

### 1. 只能做「剔除」，做不到「加权」

Open3D 的 ``registration_icp`` **不接受逐点权重**（``TransformationEstimation*``
只有标量 weight）。论文的 ``w = 1 + tanh(α)(0.5−c)`` 在这里做不到。
能做到的是「把 c 低于阈值的点排除」——等价于 w→0 那一端。

所以函数、配置项、指标一律叫 ``filter``（剔除），**不叫 weight**。
名字撒谎比功能缺失更糟：读者会以为在做加权融合，实际是把点扔了。

### 2. 点云上用 ``|n̂ · n̄|``，不是 ``(dot+1)/2``

论文的图像法向逐像素预测，符号天然连续，``(dot+1)/2`` 成立。
点云的 ``estimate_normals`` 符号是逐点随机的：同一片平面上相邻两点可能一正一负，
直接套公式会把「完全平滑的面」算成 c≈0。

**第一版试过「先一致化定向再算点积」，结果更糟**：
``orient_normals_consistent_tangent_plane`` 沿邻域传播方向，对「本没有表面」的
散点云也会硬传播出一套平滑的伪场——实测体散点云的 c 中位数被判成 **0.9+**，
而实际上那些法线是随机的。闸门就此失效。

改用 ``c = |n̂ · n̄|``：只问「方向是否共线」，不问朝向。
符号（朝向）问题归 ``normal_agreement``（ADR-0025）管，两者分工不重叠。

实测判别力（同一份真机点云，半径 0.03、30 近邻）：

| 几何 | c 中位数 | frac_low |
|---|---|---|
| 球面（有表面） | 1.000 | 0.01 |
| 球面 + 微扰 | 1.000 | 0.01 |
| 球体内散点（无表面） | 0.725 | 0.39 |
| 手设随机法线 | ≈0.50 | 高 |

第三行说明「无表面」在 ``estimate_normals`` 下仍能得到 0.72——邻域重叠让局部平面
相关。所以 ``normal_min_quality`` 守的是「明显随机」那一端，不是「完全没有表面」。

### 3. 筛选只用于求变换，fitness 的分母必须回到原始点数

这是最容易做错的地方：``fitness = 内点数 / 总点数``。如果分母换成「筛选后点数」，
fitness 会天然上升——因为被筛掉的正是难配的点。读起来像「配得更好」，
其实只是把难处藏了（与本项目一贯反对的「指标口径漂移」同构）。

实现：``src_icp``（筛过的）只喂给 ICP 求变换；``fit_eff = icp.fitness ×
len(src_icp) / len(source)``，并覆盖 ``metrics["fitness"]``。
``normal_agreement`` 本来就按原始 source 评估，不受影响。

### 4. P1-1 闸门：法向不可靠就不筛

「用一个不可靠的量去做筛选，可能比不筛选更差」。论文自己的表 6 是证据：
GT 法向 0.280 / Omnidata 0.286 / MiDaS 0.295 / **无先验 0.309**。

所以 ``normal_quality.median < max(normal_min_quality, 0.7)`` 时**放弃筛选**，
落 ``normal_filter_skipped="low_quality"`` + WARNING。另有一道：
筛完剩不到 50% 的点也放弃（``too_few``）——那等于「用半件去配整件」。

**``0.7`` 这个阈值没有真机标定**。真机 `relic_001` 的 c 中位数是多少还没量
（本轮只跑了注入实验）。它是保守默认值，等真实两期数据再定。

### 5. 默认关闭

``register.normal_filter = 0.0``。关闭时这段完全不碰 source，
``run()`` 的代码路径与 r33 之前一致。单测 ``test_off_by_default_is_bit_identical``
钉住了「同进程内两次运行变换逐位相同（atol=1e-12）」。

## 验证

### 真机（`test111.ply`，voxel=对角线/400，噪声 0.2% 对角线）

| 场景 | filter | fitness | 旋转误差 | 筛后保留 |
|---|---|---|---|---|
| 全重叠，注入 120° | 0 | **0.4391** | **144.30°** | 1.000 |
| 同上 | 0.7 | 0.9939 | 119.99° | 0.994 |
| 同上 | 0.9 | 0.9741 | 119.99° | 0.974 |
| 低重叠 60%，注入 120° | 0 | 0.9976 | 120.00° | 1.000 |
| 同上 | 0.7 | 0.9920 | 120.00° | 0.994 |
| 同上 | 0.9 | 0.9734 | 120.00° | 0.976 |

**低重叠场景不退化**（0.9976 → 0.9920），这是 P0-2 的主判据，通过。

全重叠那三行里，默认配置解出 144.30°、筛后解对——**但这是 n=1，不作结论**。
它更可能是配准本身不稳定的一次抽样（见下）。

### D1：验证时发现的严重问题——配准单次成功率只有 60~100%

为判断「7° 档从 0.03° 变成 30°」是不是本次改动引入的，用 ``git worktree`` 检出
r32 做对照，各跑 10 次：

| 版本 | 7° 注入 PASS |
|---|---|
| r32（改动前） | **6/10** |
| 本次（改动后） | **6/10** |

**完全一致** → 不是本次引入的回归。但这条数据本身比 P0-2 重要：

| 注入角度 | PASS 率 |
|---|---|
| 7° | 6/10（40% 失败） |
| 30° | 4/5 |
| 120° | 4/5 |
| 180° | 5/5 |

**r28 那张「五档 ≤0.04°」的表是单次抽样的结果，不代表稳定性。** 当时用 5 次全对
宣称「错解未再复现」，现在 10 次里 4 次错——与本项目反复记的教训完全一致：
**3~5 次样本不足以判断一个 20~40% 失败率的现象**。

根因仍是 r28 记的那条：RANSAC 内部的并行归约不受种子完全约束，初值选择在进程间
不同。本轮额外排除了两个候选：
- 法线估计**是**确定的（3 次跨进程哈希相同）；
- 输入构造（噪声、voxel）是确定的。

这条**不在 P0-2 范围内**，但它把「配准可用性」这个更根本的问题摆到了台面上。
建议优先于 P1-2 / P2 处理。

## 后果

- 新增 ``h3d/register/normals.py``（``normal_consistency`` / ``normal_quality``），
  纯 numpy + scipy，不碰 Open3D 采样与随机源。
- ``RegisterConfig`` 新增 ``normal_filter``（默认 0）与 ``normal_min_quality``（默认 0.7）。
- ``run()`` 的 metrics 新增四个键，**并且补进 ``_stage_register`` 的手写白名单**——
  这是手写白名单的第 N 次复现：``register.run`` 里算了、不写进白名单，
  脚本与报表一律读不到，而一切看起来正常。
- ``scripts/probe_normal_filter.py`` 可复现上表的对比。

## 不做的

- **不实现真正的加权 ICP**：Open3D 不支持；自己写一个加权 ICP 是新的算法工作，
  收益未验证，不在本阶段。
- **不把 c 接进 M4 贴图权重**（P1-2）：那需要另一轮 A/B，且它的判据是
  `texture_overlap`/`color_std`/`island_fill_ratio` 三数同看，独立评估。
- **不用 c 做分数**：``_icp_multi_init`` 仍按 fitness 选初值。混合打分会让
  「选哪个初值」多一个未标定的权重，而 r29 的朝向闸门已经覆盖了方向问题。
