# ADR-0002：图集继承（B1）—— 跨项目继承基准 UV 图集

- 状态：已接受
- 日期：2026-10-31
- 决策人：项目负责人（三问三答）
- 相关：`GLOSSARY.md`、《彩绘文物数字化管线_入口重构与模块构建指南》2.2 节、
  `docs/adr/0001-archive-layer.md`（B0 前置）

## 背景

指南 2.2：两个时相要逐 texel 比色，必须共用同一套 UV 展开。第 2 期若独立重新
展开，其 texel 与第 1 期不存在一一对应关系，ΔE 逐点比较完全失效。

动手前发现三件事，直接改变了工作量重心：

1. **重投影器是现成的**。`project_photos_to_texture(mesh, uv, faces, images,
   cameras, photo_dir)` 接受外部 `uv/faces` —— M4 平时传的是自己展开的结果。
   所以「把复测影像烘到基准图集」= 用基准的 mesh/uv/faces + 复测的相机/照片，
   调同一个采样器。**不需要重新展开 UV**。
2. **M4 从不落盘 UV 布局**。它只在内存里有 `uv/faces`，跑完即丢。所以「继承」
   在 B1 之前根本无法发生：第二次烘焙没有任何权威的 UV 可继承。这是本批真正的
   起点，而不是 A/B 两个时相怎么对齐。
3. **跨期相机变换是唯一「算错也不报错」的环节**。`capture_meta` 的 `t` 是
   相机中心（不是 OpenCV tvec），投影写作 `pc=(X-C)@R.T`、判 `z<0`。变换错
   一次，纹理整片错位，而 rc=0、指标看起来正常（r17 的教训）。

## 决策

### D1 复测期是**独立项目**，不是同项目内的时相子目录

`A_2026/`（基准）与 `A_2027/`（复测）各自是完整项目、各自有 `archive/`。
继承时把复测项目的影像烘到基准项目的图集上，产物落进**复测项目自己的**
`50_tex/`，并在复测项目的档案里登记一个新版本。

理由：
- 当前 `Archive._abs` 把产物路径锁在项目根内（拒绝 `../../x`），跨项目「引用
  产物」在结构上不可能；用「跨项目引用**图集版本**、产物各存各家」绕开了它；
- 不动 `paths.py` / 任务发现 / runner 执行作用域（200+ 处 `task.root` 拼接）。

代价：继承产物是「只有纹理、几何在基准项目」的资产。`CanonicalAsset.mesh_path`
留空，来源记在 `params.inherited_from`。报表必须能显示这一点，不能让它看起来
和「本期独立烘焙」一样。

**未做**：同一项目内多时相子目录（`<项目>/时相/E2/阶段成果/…`）。语义更干净，
但要改布局与 runner 作用域，留待以后。

### D2 图集是档案级实体，版本一旦登记即冻结

`archive/atlas/<version>.json` 记录：定义它的时相、`uv_digest`（UV 布局指纹）、
布局文件相对路径、尺寸、冻结时间。

- 同版本 + 同 digest → **幂等**（返回已有记录，不重写文件）；
- 同版本 + 不同 digest → 抛 `AtlasFrozen`，必须新建 `atlas-vN+1`。

理由：覆盖等于让所有基于旧图集的历史结论悄悄失效，而报表、耗时、日志全部正常。
这类「看起来成功」的失效本项目已经栽过两次（r16 手写白名单、r17 自报 rmse）。

`uv_digest` 的三条实现纪律：**统一降到 float32 再序列化**（否则 float32 落盘 →
float64 读回会判成「图集变了」，版本号无意义地一路涨）、dtype 与 shape 进哈希头、
面顺序参与（面顺序变了就是另一套 texel 对应）。

### D3 UV 布局文件必须**自包含展开后几何**

`save_uv_layout(path, uv, faces, verts=..., normals=...)` 存 `.npz`。

这条是踩出来的：`uv/faces` 的索引属于**展开后**的拓扑（xatlas 在 UV 接缝处拆分
顶点，顶点数 ≥ 原始网格）。一开始只存 `uv/faces`，继承端拿原始 PLY 承接，当场
`index 880 is out of bounds for axis 0 with size 762`。

若落到「在别的模型上恰好不越界」的情形，问题会更糟：它不报错，只是把纹理贴到
错误的位置。所以：有 `verts` 就用它重建；没有（旧版布局）则回退基准 PLY，但
**必须校验面索引范围**，越界即失败并提示「重跑一次基准期照片纹理」。

### D4 跨项目引用用限定名 `<artifact_id>@atlas-vN`

`atlas-v1` 是**项目内命名空间**：A 的 `atlas-v1` 与 B 的 `atlas-v1` 是两套完全
不同的 UV。继承产物的 `CanonicalAsset.uv_atlas_ref` 写 `relic_001@atlas-v1`，
否则报表上会出现两个都叫 v1、texel 却对不上的图集。

### D5 位姿变换的正确性判据是**投影恒等式**，不是覆盖率

`Similarity(R, t, s)` 把复测世界映射到基准世界；相机变换为

    C' = s·R·C + t
    R' = R_cam·Rᵀ / s

`R'` 含 `1/s` 因子、**不是正交矩阵**：投影只看 `x/z`、`y/z` 的比值与符号，整体
乘一个正常数不改变像素坐标；去掉 `1/s` 等于把视野缩放 1/s 倍，投影像素全错。
（`s=1` 时它自然退化为正交阵，有测试守着。）

判据采用**投影恒等式**：对任意点 X，用原相机投影得到的 `pc`，必须等于「先把 X
变换到基准系、再用变换后相机投影」得到的 `pc'`。这个判据不依赖实现细节，且能
反向验证判别力 —— 把变换用反时必须明显不等。

**刻意不用覆盖率当判据**：球体各向同性，相机搬到任意视角都还能看到球面。实测
反向变换只把 `in_frame_fraction` 从 0.799 打到 0.717，而纹素中位差从个位数跳到
30+。覆盖率正常而整片错位，正是 r17 吃过的亏。

### D6 失败一律显式，不烘「大概对」的图集

以下任一情况返回 `failed` 且**不产出纹理**：

| 情形 | 为什么不能继续 |
|---|---|
| 基准期无图集记录 | 没有 UV 定义，texel 对应无从谈起（旧版 M4 就是这种状态） |
| UV 布局缺失/损坏 | 继续会烘出全黑图集，而流程显示成功 |
| 布局与网格拓扑不符 | 面索引越界；换一个模型可能不越界，于是错得更隐蔽 |
| 自动配准被质量闸门拒绝 | 拿恒等变换去烘 = 把纹理整体错位 |
| 复测项目未建档 | 没有基准期可登记，产物会成为孤儿 |

自动配准复用 `geo_align.align_points_to_mesh`（带质量闸门、被拒时返回恒等）。
恒等在这里**不能**当成「配准成功」——它和「两期真的一模一样」无法区分。

## 后果

**正面**
- 图集继承不依赖重新展开 UV，主路径与 M4 共用同一个采样器，因此「继承出来的
  纹理质量」与「M4 自己的纹理质量」同源，性能与失败模式都一致。
- 档案里能同时存在两种纹理产物：本期独立烘焙的、继承基准图集的。`uv_atlas_ref`
  一眼区分。

**负面 / 需接受**
- **成功路径目前只有合成验证**：同一件文物的第二期真实采集数据还没有。合成自检
  （已知变换注入 → 继承 → 与基准逐 texel 比，中位差 < 6；反向变换中位差 > 30）
  能证明变换与采样正确，**不能**替代真实复测的位姿误差。
- 真实几何与真实尺寸（2048²、8 万面）的**耗时未测**。GUI 用后台线程跑估算 50 s
  量级（与 M4 同源），但这是推算值。
- 基准期若重算导致 UV 变化，需要人工新建 `atlas-vN+1`；**尚未实现**「自动把引用
  旧版本的资产标记 `atlas_stale`」。
- `CanonicalAsset` 没有 `atlas_stale` 字段；当前只能靠 `uv_atlas_ref` 比对
  `AtlasRegistry.current()` 自行判断。

## 未决

- 自动 `atlas_stale` 标记与报表列（本批未做）。
- 同一项目内多时相布局（D1 的另一条路）。
- 跨期配准的**真实**精度：`align_points_to_mesh` 是「点云→网格」，复测是网格→
  网格，两者靠顶点采样近似。真实数据上需要复核 fitness 与最终纹理的一致性。
- 图集尺寸变更（2048 → 4096）是否算新版本：当前按 `size_px` 进记录但不进
  `uv_digest`，理论上 UV 不变、图集变大可以复用同一布局 —— 未验证。

「验证 B1」之外的动作；合入后第一次打开项目时执行即可。
