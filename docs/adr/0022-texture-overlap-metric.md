# ADR-0022：纹理重叠度（设计书 §17.3 一直挂 N/A）

- 状态：已实装（2026-11-04）
- 相关：ADR-0012（多视图光度校准的上限）、ADR-0016（X3 图斑成因）
- 代码：`h3d.photo_texture`（M4 计算）、`h3d.runner._stage_quality`（M5 转手）、
  `h3d.report.html_export`（第三节新列）
- 触发：清点「已知但未做」时发现 `quality.run` 里挂着
  `"overlap": None,  # 多视图纹理重叠（M4 未实现，N/A）`

## 现象：一行 N/A 挂了几个版本

```python
"overlap": None,  # 多视角纹理重叠（M4 未实现，N/A）
```

设计书 §17.3 列了这个指标，`h3d/texture/uv.py` 的注释还写着「M5 质检的 overlap
（纹理重叠度）指标随 UV 路径启用」。**设计写了、注释写了、代码是 None。**

## 为什么它不能没有

报表里已经有 `multiview_color_std`（多视角色差）。它算的是「融合进去的那几台
相机意见差多少」——听起来像"多视图质量"，但它**读不出到底有没有第二台相机**：

| 情况 | `multiview_color_std` | 实际 |
|---|---|---|
| 10 台相机，色调一致 | 小 | 真·多视图融合，稳 |
| **1 台相机**硬投影 | **恒等于 0** | 没有任何冗余，接缝/漏色无从缓解 |

两种情况的色差都是"小"，意义完全相反。**最该报警的情况恰好是这个指标最漂亮的
情况。** 少了重叠度，`multiview_color_std` 单独读会读反。

## 决定

### D1：M4 算，M5 只转手

重叠度只能在 M4 算——那里有 `W`（每个纹素 × 每台相机的权重矩阵）。
M5 重算等于再投影一次（几十秒），且会引入第二份实现。

```python
contrib[纹素] = (W[valid] > 0).sum(axis=1)   # 有几台相机给了非零权重
```

指标两个：
- `texture_overlap` = 着色纹素上的**均值**（几台/纹素）；
- `texture_multi_view_ratio` = 有 **≥2 台**的纹素占比。

### D2：按纹素去重，不是「相机×纹素」事件

与 `back_facing_filled` / `occluded` 那类计数器**不是一回事**：那两者是一台相机
判一次就 +1，30 台能把 7 万纹素刷成 200 万（ADR 早年踩过，报表因此读出「77.8%
靠反面填充」这种与事实相反的结论）。这里一个纹素被 5 台看到就记 5，被 1 台记 1。

### D3：只在**真着色**纹素上统计

不外扩（`_bleed`）、不填洞。填出来的纹素没有相机看过，算进去会把重叠度稀释成
好看的假数——那正是本项目反复在治的那类"数字好看但不成立"。

### D4：缺键必须是 None，不是 0

M4 没跑 / 老项目没这个键 → `None` → 报表印 N/A。填 0 会被读成「没有任何相机
参与」，与"没量"是两回事。

### D5：三处同步 + 缓存版本

计算处（M4）→ manifest 白名单（`overlap` / `texture_multi_view_ratio`）→
模板（第三节新列）。`qc_metrics.json` 也落一份——判门失败时 manifest 不写，
它是唯一留档。

`CACHE_VERSION` 5 → 6：**键集合变了必须升**，否则旧缓存一直被复用，新指标
永远是 None 且不报错（这个坑踩过两次）。

## 标定：合成曲线

环绕球 + `_make_meta(n)`，同一份网格，只改相机数：

| 相机数 | `texture_overlap` | `multi_view_ratio` |
|---|---|---|
| 2 | 1.50 | 49.6% |
| 4 | 2.20 | 78.2% |
| 6 | 3.19 | 90.6% |
| 8 | 4.20 | 94.3% |
| 12 | 6.24 | 97.3% |

单调上升，量级合理，上限受相机数约束（2 台不可能 >2）。测试里钉的是**单调性**
与**定义自洽**（`overlap ≥ 1 + multi_view_ratio`），不是拍死的数字——后者会在
换相机模型时无谓地红。

## 真机：`D:/h3d_relic_test`（30 张照片，11 台可用）

| 指标 | 值 | 读法 |
|---|---|---|
| `texture_overlap` | **5.77** | 平均每个着色纹素有 5.77 台相机参与 |
| `texture_multi_view_ratio` | **98.4%** | 几乎每个纹素都有 ≥2 台 |
| `multiview_color_std` | **40.44** | 高 |
| `island_fill_ratio` | 0.8264 | <0.85，偏空 |

**这三个数放在一起才有信息**：重叠度很高（98.4% 的纹素有冗余），但色差照样
40.44 —— 说明问题不在"看不到"，而在**同一纹素上几台相机的色调差得太多**。
配合 `projected_cameras=11/30`（19 台位姿无效，ADR-0013 的老账）与岛内填充率
0.83，指向的是"少数相机承担了全部着色，且它们之间不一致"。

如果只看 `multiview_color_std=40.44`，第一反应会是"多视图融合做得差、该调权重"；
加上重叠度就知道**不是融合算法的问题**，而是可用相机太少、只能靠这 11 台的
差异硬融。这正是 `h3d verify` 之外的第二类判据：**指标要成对读**。

## 没做的事

- **不做「重叠度低就警告」的阈值**。低重叠度可能是文物形状决定的（深腔、
  镂空件的内侧本来就只有一个机位看得到），把它判成缺陷等于逼人去凑覆盖。
  报表给数、给口径，判读留给复核者。
- **不进 `accuracy.csv`**。那是质检结论表（19 列，`h3d verify` 按列核对），
  重叠度是**方法学指标**不是合格判据；塞进去会让"表头一致"这条核验跟着动，
  而它挡的是真缺陷。
- **不把 `overlap` 补进论文表**（`thesis_tables`）。先在报表里立住，等有第二件
  真机数据再谈"能不能横向比"。
