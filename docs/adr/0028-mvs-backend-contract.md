# ADR-0028：稠密重建后端契约（io/mvs）

- 状态：已采纳
- 日期：2026-11-07
- 相关：ADR-0007（阶段清单单一真源）、ADR-0020（数据来源声明）、
  `docs/文献分析-法向量引导MVS对管线的优化方向.md` P0-1

## 背景

`sfm_solve.run_dense_stereo` 直接把三条 COLMAP 命令就地拼出来：`image_undistorter`
→ `patch_match_stereo` → `stereo_fusion`，路径与参数写死在函数体里。这带来两个后果：

1. **换后端必须改业务层**。想试 PatchMatch 之外的稠密重建（例如法向引导的 MVS），
   改动会落在 `sfm_solve` 这个 1600 行的文件里，而不是落在一个可替换的模块里。
2. **没有地方记「这期是哪个后端跑的」**。跨期比对要求「同一对比链内重建后端版本
   一致」（评估报告第 5 章第六项约定），而当前连一个 `backend_id` 字段都没有。

文献分析把这件事排在 P0，理由不是「抽象好看」，而是**越晚做越贵**：一旦有了真实
两期数据，历史链的「后端不一致」就无法事后追溯。

## 决策

新增 `h3d.io.mvs`，把「稠密重建」表达为**一份可执行计划**：

```
MvsRequest(photo_dir, sparse_model, workspace, exe, options)
    ↓  backend.plan(req)
MvsPlan(dense_dir, steps[MvsStep(argv, label, heavy)], fused_path, progress())
    ↓  业务层执行（超时 / 日志 / 诊断）
fused.ply
```

- `MvsBackend` 是抽象基类，只有一个必须实现的方法 `plan()`。接口小、行为多。
- `MvsStep.heavy` 由**后端声明**哪一步是耗时段，业务层不再按「第 2 步」猜超时预算
  （原先 `i == 2` 的写法，序号一改就错配）。
- `MvsPlan.progress()` 是回调：超时诊断需要「算到第几张」，而这依赖后端的目录布局，
  所以由后端提供，业务层只把它拼进文案。
- `MvsPlan.budgets(total)` 把总预算按 `heavy` 分给各步（耗时段全拿，其余 1/4，下限 600 s）。

### 一个必须说明的偏离：契约不是 `(images, K, R, t)`

文献分析里写的是 `reconstruct(images, K, R, t, cfg)`。实现时按真实约束改了：

**COLMAP 的 `patch_match_stereo` 只认目录**（`--workspace_path` + COLMAP 格式的
sparse 模型），不接内存里的内参/外参。硬套 `(images, K, R, t)` 就得先把位姿写回
COLMAP 的 `cameras.bin`/`images.bin`——那是为了一个不存在的使用方增加一次序列化，
还要保证写出来的模型与 S1 产物逐位一致，风险大于收益。

因此契约携带的是 **`sparse_model`（后端可直接消费的模型目录）+ 语义化 `options`**。

这不削弱可插拔性：位姿已经在这个目录里，任何后端都能读；而 `options` 用的是
**后端无关语义**（`min_pixels` / `max_pixels` / `max_image_size` / `geom_consistency`），
新增后端不认识某个键时必须忽略而不是报错。

### 已知边界：只覆盖「外部命令式」后端

`MvsStep` 目前只有 `argv` 一种形态。纯 Python 推理后端（法向引导 MVS）接进来，
需要给它加「进程内调用」形态。这是**有明确扩展点的改动**，不是改契约语义。

不假装现在就支持它——那样只会让两边都不好用。ADR 如实记录边界，比含糊地声称
「可插拔」更有用。

## 验证

重构不能改行为。三层判据，从便宜到贵：

| 层 | 判据 | 结果 |
|---|---|---|
| 命令 | 三条 argv 与重构前**逐字相同**（期望值手写，不从实现里读） | 9 条测试 |
| 行为 | 指纹续算 / 超时诊断 / 参数开关 14 条既有测试不变 | 全绿 |
| 产物 | 同一份 sparse + 照片，重构前后各跑一次 dense，比**点集统计量** | 见下 |

产物层的实测（真机 `relic_001`，30 张 2399px，`max_image_size=480`，单遍）：

| 对比 | 点数 | 位置不同的点 | max / 对角线 |
|---|---|---|---|
| **旧 vs 旧**（同一份代码跑两次） | 130,921 vs **130,929**（差 8） | 1.87% | **1.0e-3** |
| **旧 vs 新**（重构前后） | 130,921 vs 130,921（差 0） | 1.40% | **0.86e-3** |

**重构前后的差异比旧代码自比还小。** 所以本次重构在噪声范围内无影响。

### D1：验证时发现——COLMAP 稠密重建本身不可逐位复现

这是本次最意外的收获，比契约本身更重要：

> 同一份代码、同一份输入、同一台机器，`patch_match_stereo` + `stereo_fusion`
> 跑两次，点数从 130,921 变成 130,929，1.87% 的点位置不同，最大偏差达包围盒
> 对角线的 **1.0e-3**。

来源是 GPU 并行归约与融合阶段的点取舍顺序，**不是调用方的问题**。因此：

- 「`fused.ply` 哈希相同」**不能**作为等价性判据——它会在正常输入上恒假，
  和「判据在垃圾输入上恒真」一样，都不算判据。
- 判据改为统计口径：点数相对差 ≤0.1% 且双向最近邻中位距离 = 0 且
  max ≤ 2e-3 × 对角线。`scripts/compare_point_sets.py` 实现了它。

**对 X1 的硬约束（需要单独记一笔）**：1.0e-3 × 对角线，若模型对角线 300 mm，
这个噪声是 **0.3 mm**；而 X1 要检的是 0.5 mm 量级的形变——噪声达到信号的 60%。
后果有两条：

1. **不能靠「重跑某一期」来修正数据**：重跑得到的是另一份点云，不是同一份的更准版本。
2. 跨期差分若要引用数值，必须声明这个噪声下限；或者在同一份 dense 产物上做差分
   （图集继承那条路已经是这么做的）。

这与 ADR-0026（随机消费者定种子）是**不同**的一类：那一类是我们能控制的，
这一类是第三方后端的行为——只能承认、量出来、写清楚，不能"修好"。

## 后果

- `run_dense_stereo` 的**签名与返回值不变**，两个调用点（`_stage_sfm`、
  `incremental_dense_new_views`）一行没改。
- `_count_depth_maps` 从 `sfm_solve` 下沉到 `io.mvs.colmap_pm`，业务层不再知道
  COLMAP 的 `stereo/depth_maps/*.photometric.bin` 布局。
- `backend_id` / `backend_version` 就位，P0-3（写进资产元数据与内容哈希）可以直接接。
- 换后端 = `get_backend("...")` 换个名字 + 实现 `plan()`。未知后端名**立刻抛**，
  不静默回退（静默回退会让「配置写错」表现为「用别的后端跑出别的点云」）。

## 备选方案

| 方案 | 为什么不选 |
|---|---|
| 只加一层薄函数 `dense_backend(cmd_list)` | 命令还是业务层拼的，换后端照样改 `sfm_solve` |
| 用 `(images, K, R, t)` 严格对齐论文接口 | 需要为 COLMAP 额外序列化一份模型，且与 S1 产物的位姿一致性无法保证 |
| 引入 ABC 之外的后端插件注册（entry points） | 当前只有一个后端，插件机制是过度设计；`BACKENDS` 字典够用 |
